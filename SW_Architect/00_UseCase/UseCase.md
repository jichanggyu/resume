# UC01 – 로봇 정지 (Robot Stop)

## 개요

| 항목 | 내용 |
|------|------|
| **유즈케이스 ID** | UC01 |
| **유즈케이스 명** | 로봇 정지 (Emergency / Manual Stop) |
| **관련 기능 요구사항** | F1-1. 로봇 정지 |
| **주 액터** | 운영자 (Web UI 사용자) |
| **목적** | 로봇이 현재 수행 중인 모든 동작을 즉시 중단하도록 명령한다. |

---

## 사전 조건

- 로봇이 동작 중이거나 대기 중이어야 한다.
- 웹 UI와 로봇이 정상적으로 연결되어 있어야 한다.

## 후 조건

- 로봇이 모든 동작을 중지한 상태로 전환된다.
- 상태 표시창에 “정지됨(Stopped)”이 표시된다.
- 정지 후 재개하려면 별도의 Start 또는 Reset 명령이 필요하다.

---

## 기본 흐름

1. 운영자가 Web UI에서 [정지] 버튼을 클릭한다.
2. Web UI는 FastAPI에 `POST /api/robot/stop` 요청을 보낸다.
3. FastAPI는 ROS2 토픽 `/robot/cmd_stop`에 정지 명령을 발행한다.
4. `Schedular Node`는 현재 실행 중인 시나리오 또는 작업을 중단한다.
5. `Command Executor Node`는 현재 명령을 멈추고 동작을 중단한다.
6. `H/W Node`는 각 장치(팔, 허리 등)를 정지 상태로 전환한다.
7. `Status Node`는 현재 상태를 `"stopped"`로 갱신하여 상태 토픽으로 발행한다.
8. FastAPI는 해당 상태를 전달하고, UI는 이를 표시한다.
---

## 예외 흐름

- **E1: ROS 통신 장애**
  - FastAPI가 ROS2 노드와 통신할 수 없는 경우
  - → UI에 통신 오류 메시지를 출력하고 재시도 옵션 제공

- **E2: 로봇이 이미 정지 상태**
  - 이미 정지 상태인데 정지 명령을 추가로 보낸 경우
  - → UI에 “이미 정지 상태입니다” 메시지를 표시 (에러 아님)

- **E3: 정지 중 충돌 위험**
  - 작업 도중 정지 명령으로 인해 팔이 충돌 가능 위치에 정지할 수 있음
  - → 정지와 함께 “주의: 위험 위치에 정지됨” 경고 표시

---

## 통신 흐름

| 송신자 | 수신자 | 방식 | 메시지 |
|--------|--------|------|--------|
| Web UI | FastAPI | HTTP POST | `/api/robot/stop` |
| FastAPI | ROS2 | ROS2 Topic | `/robot/cmd_stop` |
| Schedular Node | Command Executor Node | 내부 제어 요청 | 작업 중단 명령 |
| Command Executor Node | H/W Node | ROS2 Topic or Action | 장치 정지 명령 |
| H/W Node | 내부 hardware_node | 하드웨어 I/O | 각 장치 정지 |
| Status Node | FastAPI | ROS2 Topic | `/robot/status` = "stopped" |
| FastAPI | Web UI | WebSocket or Polling | 정지 완료 상태 전달 |

---

## 비고

- 정지 기능은 안전과 직결되므로 1초 이내 응답을 목표로 한다.
- 필요 시 하드웨어 기반 정지(비상 정지 버튼 등)와 통합될 수 있음.
- ROS2 제어 노드는 정지 명령을 수신했을 때, 현재 동작을 안전하게 취소 또는 중단해야 한다.

# UC02 – 좌표 기반 이동 (Coordinate Move)

## 개요

| 항목 | 내용 |
|------|------|
| **유즈케이스 ID** | UC02 |
| **유즈케이스 명** | 좌표 기반 이동 |
| **관련 기능 요구사항** | F1-2. 좌표 기반 이동 |
| **주 액터** | 운영자 (Web UI 사용자) |
| **목적** | 로봇이 사용자가 입력한 특정 위치(x, y, θ)로 이동할 수 있어야 한다. |

---

## 사전 조건

- 로봇이 정지 또는 대기 상태여야 한다.
- 이동 명령에 사용되는 좌표가 작업 공간 내 유효 범위여야 한다.
- 로봇과 웹 UI, FastAPI, ROS2 간 통신이 활성화되어 있어야 한다.

## 후 조건

- 로봇이 요청된 좌표로 이동을 완료한다.
- 웹 UI에 도착 위치, 이동 결과, 이동 성공 여부가 표시된다.

---

## 기본 흐름

1. 운영자가 Web UI에서 좌표를 입력하고 [이동] 버튼을 클릭한다.
2. Web UI는 FastAPI에 `POST /api/robot/move` 요청을 보낸다 (좌표 포함).
3. FastAPI는 해당 pose 정보를 포함하여 ROS2에 `/robot/cmd_move_pose` 토픽을 publish한다.
4. `Command Executor Node`는 이동 명령을 수신하고, 목표 좌표로의 동작 계획을 수립한다.
5. `H/W Node`는 해당 좌표로 로봇팔을 이동시킨다 (Rainbow Robotics PGM 사용).
6. 이동이 완료되면 상태 메시지가 `Status Node`에 전달된다.
7. `Status Node`는 "이동 완료" 상태를 FastAPI에 전달한다.
8. FastAPI는 상태를 Web UI로 전달하고, UI에 `"이동 완료"` 메시지를 표시한다.

---

## 예외 흐름

- **E1: 좌표 유효성 오류**
  - 입력한 좌표가 작업 가능 범위를 벗어난 경우
  - → UI에 “유효하지 않은 좌표입니다” 알림 표시

- **E2: 이동 중 충돌 가능 경로**
  - 이동 경로에 장애물이 있어 충돌 위험이 예상될 경우
  - → ROS2가 이동을 중단하고 경고 메시지를 전송  
  - → UI에 “이동 불가: 장애물 감지” 표시

- **E3: 이동 실패 (기계적 문제)**
  - 휠, 모터, 센서 오류 등으로 인해 이동이 완료되지 못한 경우
  - → UI에 “이동 실패” 메시지 + 상세 오류 표시

---

## 통신 흐름

| 송신자 | 수신자 | 방식 | 메시지 |
|--------|--------|------|--------|
| Web UI | FastAPI | HTTP POST | `/api/robot/move` (pose 포함) |
| FastAPI | ROS2 | ROS2 Topic | `/robot/cmd_move_pose` |
| Command Executor Node | H/W Node | ROS2 Action or Topic | 지정 pose로 이동 요청 |
| H/W Node | Status Node | ROS2 Topic | 이동 완료/실패 상태 전송 |
| Status Node | FastAPI | ROS2 Topic | `/robot/status` = "completed" or "failed" |
| FastAPI | Web UI | WebSocket or 응답 | 이동 결과 표시 |

---

## 비고

- 좌표 이동은 작업 공간 내 안전한 경로 계산을 포함해야 한다.
- 향후 경로 시각화, 경로 미리보기 기능과도 연계될 수 있음.
- ROS2 이동 노드는 경로 계획 + 이동 제어 + 장애물 회피 기능을 포함해야 함.

# UC03 – 초기화 위치 이동 (Reset to Home Position)

## 개요

| 항목 | 내용 |
|------|------|
| **유즈케이스 ID** | UC03 |
| **유즈케이스 명** | 초기화 위치 이동 |
| **관련 기능 요구사항** | F1-3. 초기화 위치 이동 |
| **주 액터** | 운영자 (Web UI 사용자) |
| **목적** | 로봇을 안전한 초기 위치(홈 포지션)로 복귀시켜 다음 작업을 준비한다. |

---

## 사전 조건

- 로봇이 동작 중이 아니거나 정지 상태여야 한다.
- 홈 위치(기본 자세)의 좌표값이 사전에 시스템에 등록되어 있어야 한다.
- 로봇과 UI, 백엔드, ROS2 간 통신이 정상 상태여야 한다.

## 후 조건

- 로봇이 지정된 초기 위치(6D pose: x, y, z, rx, ry, rz)로 이동한다.
- UI에서 로봇이 초기 위치에 도달했음을 확인할 수 있다.
- 이후 작업 명령 수행이 가능해진다.

---

## 기본 흐름

1. 운영자가 Web UI에서 [초기화] 버튼을 클릭한다.
2. Web UI는 FastAPI에 `POST /api/robot/reset_pose` 요청을 보낸다.
3. FastAPI는 ROS2에 `/robot/cmd_reset_pose` 토픽으로 초기화 명령을 발행한다.
4. `Command Executor Node`는 사전 정의된 pose를 참조하여 이동 명령을 생성한다.
5. `H/W Node`는 로봇팔 또는 관련 장치를 해당 위치로 이동시킨다.
6. 이동 완료 후 상태가 `Status Node`로 전달된다.
7. FastAPI는 상태를 수신하고, Web UI에 `"초기화 완료"` 메시지를 표시한다.

---

## 예외 흐름

- **E1: 초기화 좌표 미설정**  
  시스템에 초기 위치 값이 정의되어 있지 않은 경우  
  → UI에 “초기 위치가 설정되지 않았습니다” 오류 표시

- **E2: 경로 상 장애물 존재**  
  초기 위치로 이동하는 경로에 장애물이 존재하는 경우  
  → ROS2가 이동을 중단하고 경고 메시지 전송  
  → UI에 “초기화 이동 실패: 경로 상 장애물 감지” 표시

- **E3: 이동 실패**  
  로봇이 초기 위치로 이동 중 기계적 문제 발생  
  → UI에 오류 메시지 및 현재 위치 표시

---

## 통신 흐름

| 송신자 | 수신자 | 방식 | 메시지 |
|--------|--------|------|--------|
| Web UI | FastAPI | HTTP POST | `/api/robot/reset_pose` |
| FastAPI | ROS2 | ROS2 Topic | `/robot/cmd_reset_pose` |
| Command Executor Node | H/W Node | ROS2 Topic or Action | 초기화 위치 이동 명령 |
| H/W Node | Status Node | ROS2 Topic | "초기화 완료" 또는 "실패" |
| Status Node | FastAPI | ROS2 Topic | `/robot/status` = "home_completed" |
| FastAPI | Web UI | WebSocket or 응답 | 결과 상태 표시 |

---

## 비고

- 초기화 위치는 작업 시작 전 안전한 기준 자세로 중요함.
- 필요 시 각 작업 전에 자동 초기화 과정을 포함하도록 설계 가능.
- ROS2에서는 MoveIt, Nav2 등을 활용한 포즈 기반 이동 제어 가능.

# UC04 – 로봇 위치 정보 표시 (Display Robot Position)

## 개요

| 항목 | 내용 |
|------|------|
| **유즈케이스 ID** | UC04 |
| **유즈케이스 명** | 로봇 위치 정보 표시 |
| **관련 기능 요구사항** | F2-1. 로봇 위치 정보 표시 |
| **주 액터** | 운영자 (Web UI 사용자) |
| **목적** | 로봇의 현재 위치 및 자세(Pose)를 실시간으로 확인한다. |

---

## 사전 조건

- 로봇은 ROS2에서 현재 pose(x, y, z, rx, ry, rz)를 주기적으로 브로드캐스트해야 한다.
- 웹 UI는 실시간 위치 정보를 구독하거나 갱신할 수 있어야 한다.

## 후 조건

- 운영자는 로봇의 실시간 위치(Pose)를 UI 상에서 확인할 수 있다.
- UI에는 숫자 값 또는 시각화된 형태로 위치가 표현된다.

---

## 기본 흐름

1. `Status Node`는 로봇의 현재 위치(x, y, z, rx, ry, rz)를 주기적으로 계산한다.
2. 해당 위치 정보를 ROS2 토픽(`/robot/pose`)으로 publish한다.
3. FastAPI는 이 토픽을 구독하여 실시간으로 수신한다.
4. FastAPI는 수신된 pose 데이터를 WebSocket 또는 API 응답을 통해 Web UI에 전달한다.
5. Web UI는 좌표 및 자세 정보를 표시한다 (텍스트, 지도, 3D 뷰 등).

---

## 예외 흐름

- **E1: ROS 위치 데이터 수신 실패**  
  ROS2에서 pose 데이터를 수신하지 못한 경우  
  → UI에 “위치 정보를 수신할 수 없습니다” 경고 표시

- **E2: UI 연결 끊김**  
  네트워크 문제로 위치 정보 수신 불가  
  → UI에 자동 재연결 시도 표시 또는 “연결 끊김” 알림 표시

---

## 통신 흐름

| 송신자 | 수신자 | 방식 | 메시지 |
|--------|--------|------|--------|
| Status Node | ROS2 | ROS2 Topic | `/robot/pose` (PoseStamped 또는 Pose) |
| FastAPI | Web UI | WebSocket or REST API | 실시간 pose 데이터 전송 |
| Web UI | 화면 | 시각화 | 위치 텍스트, 지도, 3D 모델 등 표시 |


---

## 비고

- 위치 정보는 단순 텍스트 표시 외에도 WebGL 또는 2D Canvas를 통한 시각화가 권장된다.
- 데이터가 1초 이상 끊길 경우 UI 경고 메시지를 표시하도록 설계 필요.

# UC05 – 현재 수행 작업 표시 (Display Current Task)

## 개요

| 항목 | 내용 |
|------|------|
| **유즈케이스 ID** | UC05 |
| **유즈케이스 명** | 현재 수행 작업 표시 |
| **관련 기능 요구사항** | F2-2. 현재 수행 작업 표시 |
| **주 액터** | 운영자 (Web UI 사용자) |
| **목적** | 로봇이 현재 어떤 작업(예: Pick, Place, Door Open 등)을 수행 중인지 실시간으로 확인한다. |

---

## 사전 조건

- ROS2 시스템 내 작업 상태를 정의하고, 현재 작업 상태를 발행하는 구조가 존재해야 한다.
- 웹 UI와 FastAPI가 작업 상태를 수신할 수 있어야 한다.

## 후 조건

- 운영자는 현재 로봇이 수행 중인 작업을 실시간으로 확인할 수 있다.
- 작업명은 UI에 명확한 텍스트 또는 아이콘 형태로 표시된다.

---

## 기본 흐름

1. `Schedular Node` 또는 `Command Executor Node`는 작업 수행 시 현재 작업 ID 또는 명칭을 상태로 발행한다.
2. `Status Node`는 해당 작업 정보를 가공 또는 그대로 relay하여 ROS2 토픽(`/robot/task`)에 publish한다.
3. FastAPI는 이 작업 상태 토픽을 구독하고 Web UI에 전달한다.
4. Web UI는 현재 작업 상태를 텍스트 또는 상태 뱃지로 표시한다.

---

## 예외 흐름

- **E1: 상태 메시지 미수신**  
  작업 상태 메시지를 일정 시간 이상 수신하지 못한 경우  
  → UI에 “작업 상태 없음” 또는 회색 상태 표시

- **E2: 알 수 없는 작업 ID**  
  정의되지 않은 작업 코드가 전달된 경우  
  → UI에 “Unknown Task” 또는 코드 그대로 출력

---

## 통신 흐름

| 송신자 | 수신자 | 방식 | 메시지 |
|--------|--------|------|--------|
| Schedular Node or Command Executor Node | Status Node | 내부 공유 | 현재 작업 ID 또는 이름 전달 |
| Status Node | ROS2 Topic | `/robot/task` |
| FastAPI | Web UI | WebSocket or Polling | 현재 작업 상태 전달 |
| Web UI | UI 컴포넌트 | 시각화 | `"현재 작업: Pick"` 등 텍스트 표시 |

---

## 비고

- 작업 상태는 내부적으로 `작업ID + 상태코드` 구조로 관리 가능 (예: `PICK_START`, `PLACE_DONE`)
- 필요시 작업 시작~완료까지의 타이머 기능도 UI에 표시 가능
- 멀티태스크 환경이라면 서브태스크도 병행 표시 고려

| **목적** | 로봇의 배터리 잔량 및 충전 상태를 실시간으로 확인한다. |

---

## 사전 조건

- 배터리 관련 센서 또는 제어 노드가 ROS2에서 상태를 주기적으로 발행해야 한다.
- FastAPI가 배터리 상태를 수신하여 UI로 전달할 수 있어야 한다.

## 후 조건

- UI에서 배터리 잔량(%)과 충전 상태가 표시된다.
- 경고/알람 기준 이하일 경우 시각적으로 경고 표시가 된다.

---

## 기본 흐름

1. `Status Node`는 배터리 잔량(%) 및 상태를 주기적으로 수집한다.
2. 해당 정보를 `/robot/battery` 토픽으로 publish한다.
3. FastAPI는 이 토픽을 구독하고 최신 배터리 상태를 수신한다.
4. FastAPI는 WebSocket 또는 REST 응답으로 Web UI에 상태를 전달한다.
5. Web UI는 배터리 정보를 게이지, 숫자 또는 경고 아이콘으로 표시한다.

---

## 예외 흐름

- **E1: 배터리 정보 없음**  
  센서 또는 ROS 노드에서 배터리 정보를 발행하지 않을 경우  
  → UI에 “정보 없음” 또는 “-” 표시

- **E2: 데이터 이상**  
  잔량 값이 0% 미만 또는 100% 초과 등 이상치일 경우  
  → 로그 기록 및 “배터리 오류” 상태 표시

---

## 통신 흐름

| 송신자 | 수신자 | 방식 | 메시지 |
|--------|--------|------|--------|
| Status Node | ROS2 Topic | `/robot/battery` (예: std_msgs/Float32 또는 custom msg) |
| FastAPI | Web UI | WebSocket or REST API | 실시간 배터리 퍼센트 전달 |
| Web UI | UI 컴포넌트 | 시각화 | 퍼센트 게이지, 숫자, 아이콘 등 표시 |

---

## 비고

- 배터리 잔량 임계값은 예: 20% 이하에서 경고, 10% 이하에서 비상 멈춤 가능
- 향후 충전 스테이션 연동 시 자동 복귀 로직과 연결 가능
- 배터리 상태 외에 온도, 전류, 전압 등 상세 정보 표시 옵션도 고려 가능

## 사전 조건

- 각 구성 요소는 일정 주기로 “상태 alive/ping 메시지”를 발행해야 한다.
- 백엔드에서는 각 노드나 모듈과의 연결 상태를 주기적으로 확인해야 한다.

## 후 조건

- UI에서 각 노드 및 주요 구성요소의 연결 상태(정상/끊김)를 확인할 수 있다.

---

## 기본 흐름

1. `Status Node` 또는 FastAPI는 ROS2 노드들과의 상태 heartbeat 또는 주기적 토픽 수신 여부를 모니터링한다.
2. 일정 시간 내 상태 메시지가 도착하지 않으면 `"끊김"` 상태로 간주한다.
3. FastAPI는 현재 연결 상태(정상/끊김)를 WebSocket 또는 응답 API로 UI에 전달한다.
4. Web UI는 연결 상태를 색상/아이콘/텍스트 등으로 시각화한다.
---

## 예외 흐름

- **E1: 특정 노드 미응답**  
  특정 ROS2 노드가 일정 시간 이상 상태 메시지를 발행하지 않는 경우  
  → UI에 “Node 응답 없음” 또는 “통신 끊김” 표시

- **E2: FastAPI ↔ ROS 연결 오류**  
  내부 bridge 또는 통신 라우팅에 문제가 발생한 경우  
  → 모든 구성 요소에 대해 “통신 장애” 상태 표시

---

## 통신 흐름

| 송신자 | 수신자 | 방식 | 메시지 |
|--------|--------|------|--------|
| ROS2 각 노드 | Status Node | ROS2 Topic | 상태 heartbeat 또는 ping |
| Status Node | FastAPI | 내부 모니터링 | 통신 상태 판단 결과 전달 |
| FastAPI | Web UI | WebSocket or REST | `"정상"`, `"끊김"`, `"지연"` 등의 상태 전달 |
| Web UI | 화면 표시 | 시각화 | 연결 상태 표시 아이콘, 컬러 상태 등 |

---

## 비고

- 연결 상태는 UI 상단 또는 별도 “시스템 상태” 영역에서 표시하는 것이 일반적
- 응답 시간 기준 예: 2초 이상 미응답 시 “끊김” 표시, 다시 수신되면 자동 회복
- 향후 알림 시스템과 연계하여 관리자에게 즉시 알림 전송 가능

# UC08 – 작업 순서 변경 (Modify Task Sequence)

## 개요

| 항목 | 내용 |

| **주 액터** | 운영자 (Web UI 사용자) |
| **목적** | 로봇이 수행할 작업의 순서를 사용자에 의해 변경할 수 있어야 한다. |

---

## 사전 조건

- 현재 등록된 작업 시퀀스가 시스템에 존재해야 한다.
- 로봇이 “정지” 또는 “대기” 상태여야 작업 순서를 수정할 수 있다.

## 후 조건

- 새로운 작업 순서가 적용되어 이후 로봇 동작에 반영된다.
- UI에 변경된 순서가 실시간으로 표시된다.

---

## 기본 흐름

1. 사용자가 Web UI에서 작업 흐름 편집 화면에 진입한다.
2. UI는 작업 항목 리스트를 FastAPI를 통해 로딩한다.
3. 사용자는 Drag & Drop 또는 순번 선택 방식으로 작업 순서를 재구성한다.
4. [저장/적용] 버튼을 누르면 Web UI는 FastAPI에 `POST /api/robot/task_sequence`로 작업 순서를 전송한다.
5. FastAPI는 해당 리스트를 ROS2의 `/robot/task_sequence` 토픽 또는 서비스로 전달한다.
6. `Schedular Node`는 해당 순서를 내부 큐에 저장하고 상태를 `"작업 흐름 설정됨"`으로 전환한다.
7. FastAPI는 UI에 설정 성공 여부를 반환하고, UI는 `"작업 흐름 설정 완료"`를 표시한다.

---

## 예외 흐름

- **E1: 수행 중 작업은 변경 불가**  
  현재 진행 중인 작업은 순서 변경 대상에서 제외됨  
  → UI에 “현재 수행 중인 작업은 변경할 수 없습니다” 표시

- **E2: 유효하지 않은 작업 포함**  
  정의되지 않은 작업 ID가 포함될 경우  
  → UI에 오류 메시지 및 원래 상태로 롤백

---

## 통신 흐름

| 송신자 | 수신자 | 방식 | 메시지 |
|--------|--------|------|--------|
| Web UI | FastAPI | HTTP POST | `/api/robot/task_sequence` (작업 ID 리스트 포함) |
| FastAPI | ROS2 | ROS2 Topic or Service | `/robot/task_sequence` |
| Schedular Node | 내부 저장 | 작업 순서 큐 저장 |
| FastAPI | Web UI | HTTP 응답 or WebSocket | `"설정 완료"` 메시지 표시 |

---

## 비고

- 작업 순서는 사전에 정의된 시나리오 또는 사용자 지정 시나리오 기반으로 구성 가능
- 변경된 작업 순서는 로깅 및 이력 저장 필요
- 향후 ACS 연동 시 상위에서 시나리오가 내려오는 구조로 확장 가능

# UC09 – 작업 건너뛰기 / 재시도 (Skip or Retry Task)

## 개요

| 항목 | 내용 |
|------|------|
| **유즈케이스 ID** | UC09 |
| **유즈케이스 명** | 작업 흐름 변경 |
| **관련 기능 요구사항** | F4-2. 작업 순서 변경 |
| **주 액터** | 운영자 (Web UI 사용자) |
| **목적** | 이미 설정된 작업 흐름의 순서를 실시간으로 수정하여, 유연한 제어가 가능하도록 한다. |

---

## 사전 조건

- 전환 대상 시나리오가 시스템에 사전 정의되어 있어야 한다.
- 현재 시나리오가 정지 가능 상태이거나 전환이 허용된 조건이어야 한다.
- Schedular Node가 시나리오 전환을 지원해야 한다.

---

## 후 조건

- 기존 시나리오는 종료되고, 새 시나리오가 적용된다.
- UI에 전환 성공 여부가 표시된다.

---

## 기본 흐름

###

1. 운영자가 Web UI에서 새로운 시나리오를 선택하고 [전환] 버튼을 클릭한다.
2. Web UI는 FastAPI에 `POST /api/robot/scenario/switch` 요청을 보낸다.
3. FastAPI는 선택된 시나리오 ID를 ROS2의 `/robot/scenario_switch` 토픽 또는 서비스로 전달한다.
4. `Schedular Node`는 현재 시나리오를 종료하고, 새로운 시나리오를 로드한다.
5. 내부 작업 큐를 초기화하고 새 작업 흐름을 구성한다.
6. 상태 노드는 `"시나리오 전환 완료"` 상태를 발행한다.
7. FastAPI는 상태를 수신하고 UI에 전환 성공 여부를 표시한다.

---

## 예외 흐름

- **E1: 재시도 제한 초과**  
  동일 작업에 대해 재시도 횟수 초과 시  
  → UI에 “재시도 제한 초과” 메시지 표시

- **E2: Skip 불가 작업**  
  시스템상 반드시 수행해야 하는 작업을 Skip 요청한 경우  
  → “건너뛰기 불가한 작업입니다” 경고 표시

---

## 통신 흐름

| 송신자 | 수신자 | 방식 | 메시지 |
|--------|--------|------|--------|
| Web UI | FastAPI | HTTP POST | `/api/robot/scenario/switch` (시나리오 ID) |
| FastAPI | ROS2 | ROS2 Topic or Service | `/robot/scenario_switch` |
| Schedular Node | 내부 처리 | 현재 시나리오 종료 + 신규 로드 |
| Status Node | ROS2 Topic | `/robot/status` = "시나리오 전환 완료" |
| FastAPI | Web UI | WebSocket or 응답 | 결과 메시지 전달 |

---

## 비고

- 재시도 시 이전 상태 복원(팔 위치 등)이 필요한 경우 별도 리셋 절차 포함 가능
- 각 작업의 Skip/Retry 허용 여부는 설정으로 제어 가능
- 작업별 재시도 횟수 제한(예: 최대 3회) 정책 필요

# UC11 – Pick 명령 (Pick Command)

## 개요

| 항목 | 내용 |
|------|------|
| **유즈케이스 ID** | UC11 |
| **유즈케이스 명** | Pick 명령 |
| **관련 기능 요구사항** | F5-1. Pick 명령 |
| **주 액터** | 운영자 (Web UI 사용자) |
| **목적** | 로봇이 지정된 대상 물체를 비전 기반 파지점에서 픽업한다. |

---

## 사전 조건

- Pick 대상 물체가 카메라 시야 내에 존재해야 한다.
- 비전 시스템이 활성화되어 있어야 하며, 파지점 추출이 가능해야 한다.
- 로봇 팔이 대기 상태이거나 다른 작업 수행 중이 아니어야 한다.

## 후 조건

- 로봇이 파지점에 도달하고 물체를 안정적으로 파지한다.
- Pick 성공 여부가 UI에 표시되고 다음 동작으로 이어질 준비가 된다.

---

## 기본 흐름

1. 사용자가 Pick 명령을 UI에서 실행하거나, Schedular Node가 Pick 단계에 진입한다.
2. Command Executor Node는 Pick 명령을 시작한다.
3. Vision Node에 파지점을 요청한다 (특징점 추출 → 후보 생성 → 최적 파지점 선택).
4. Vision Node는 최적 파지점(Pose) 데이터를 반환한다.
5. Command Executor Node는 H/W Node에 해당 파지점으로 이동 및 파지 명령을 보낸다.
6. H/W Node는 로봇팔을 움직여 파지를 수행한다.
7. 결과 상태가 Status Node에 전달된다.

## 사전 조건

- 허리 보정용 모션이 정의되어 있어야 한다.
- 로봇이 정지 상태이거나 대기 상태여야 한다.

## 후 조건

- 로봇 상체가 기준 위치에 대해 정렬된다.
- 이후 Pick/Place 등의 동작 정확도가 향상된다.

---

## 기본 흐름

6. H/W Node에 허리 회전 명령을 보낸다 (예: 0° + Δθ).
7. H/W Node는 해당 각도로 허리를 회전시키고 완료 여부를 판단한다.
8. 결과는 status_node를 통해 FastAPI로 전달되며, UI에 표시된다.

---

# UC16 – 카메라 이미지 입력 (Capture Camera Image)

## 개요

| 항목 | 내용 |
|------|------|
| **유즈케이스 ID** | UC16 |
| **유즈케이스 명** | 카메라 이미지 입력 |
| **관련 기능 요구사항** | F6-1. 카메라 이미지 입력 |
| **주 액터** | 로봇 제어 노드 (ROS2 내부 액터) |
| **목적** | 로봇이 파지점을 판단하기 위해 실시간 카메라 이미지를 획득한다. |

---

## 사전 조건

- 카메라(3D 또는 2D)가 연결되어 있고 정상적으로 작동 중이어야 한다.
- 카메라 이미지 스트림 또는 요청 기반 프레임 캡처가 가능해야 한다.

## 후 조건

- 실시간 이미지 데이터가 ROS2로 전달되고, 비전 노드에서 처리할 수 있는 상태가 된다.

---

## 기본 흐름

1. 카메라 드라이버 또는 센서 노드가 실시간 이미지 프레임을 `/camera/image_raw` 등의 토픽으로 publish한다.
2. Vision Node는 해당 토픽을 구독(subscribe)하여 이미지를 수신한다.
3. 수신된 이미지는 내부 처리 큐에 적재되거나 즉시 후속 프로세싱(특징점 추출 등)에 사용된다.
4. 필요 시, Vision Node는 수신된 이미지를 로그 저장하거나 디버깅용으로 publish한다.

---

## 예외 흐름

## 사전 조건

- 비전 노드는 이미지 입력을 정상적으로 수신해야 한다.
- 이미지 해상도 및 포맷이 사전 정의된 조건과 일치해야 한다.

## 후 조건

- 이미지 내에서 검출된 특징점 리스트가 생성되고, 이후 파지 후보 영역 계산에 전달된다.

3. 특징점(좌표, 방향, 스케일 등)이 추출된다.
4. 추출된 특징점은 내부에서 보관되며, 필요 시 `/vision/feature_points` 토픽으로 publish된다.
5. 이후 UC18(파지점 계산)에 입력으로 사용된다.

---

  → "이미지 처리 실패: 포맷 오류" 로그 및 예외 처리

- **E2: 특징점 없음**  
  특징점이 충분히 검출되지 않거나 noise만 존재할 경우  
  → “유효한 특징 없음” 경고 메시지 출력

---

## 비고

- 추출 신뢰도(score) 기반으로 필터링하여 품질 보장
- 특징점은 다음 단계인 파지 후보 계산에 직접 활용됨

# UC18 – 파지 후보 영역 계산 (Grasp Candidate Generation)

## 개요

| 항목 | 내용 |
|------|------|
| **유즈케이스 ID** | UC18 |
| **유즈케이스 명** | 파지 후보 영역 계산 |

| **주 액터** | 비전 노드 (ROS2 내부 액터) |
| **목적** | 추출된 특징점을 바탕으로 로봇이 집을 수 있는 파지 가능 영역들을 생성한다. |

---

## 사전 조건

- 특징점 리스트가 유효하게 추출되어야 한다.
- 파지 영역을 계산할 수 있는 알고리즘 또는 모델이 내장되어 있어야 한다.

## 후 조건

- 복수의 파지 후보 영역(좌표, 각도, 신뢰도 등)이 생성되어 구조화된 데이터로 저장된다.
- 이후 단계에서 최적 파지점 선정 알고리즘에 전달된다.

---

## 기본 흐름

1. Vision Node는 특징점 리스트 또는 이미지(OR 양쪽)를 입력으로 받는다.
2. 내부 파지점 생성 알고리즘을 실행하여 grasp 후보 좌표들을 계산한다.
3. 각 파지점 후보는 다음의 정보를 포함한다:  
   - 위치 (x, y, z)  
   - 방향 (rx, ry, rz)  
   - 신뢰도 또는 점수 (score)
4. 후보 리스트는 내부적으로 저장되며, 필요 시 `/vision/grasp_candidates` 토픽으로 publish된다.

---

## 예외 흐름

- **E1: 파지 조건 미달**  
  - 파지 가능 조건(면적, 평탄성, 거리 등)을 충족하는 특징이 부족한 경우  
  → “파지 후보 없음” 로그 기록 및 상위 처리로 실패 전달

- **E2: 후보 생성 실패**  
  - 알고리즘 내부 오류 또는 데이터 이상  
  → “파지 영역 계산 실패” 메시지 출력

---

## 통신 흐름

| 송신자 | 수신자 | 방식 | 메시지 |
|--------|--------|------|--------|
| Vision Node | Vision Node 내부 | 로컬 호출 | 특징점 기반 파지점 계산 |
| Vision Node | ROS2 Topic | `/vision/grasp_candidates` (custom msg list) |

---

## 비고

- 후보 생성 수는 임계값 이상일 경우 top-N 필터링 가능

- GraspNet 등 학습 기반 방법을 사용하는 경우도 적용 가능

## 사전 조건

- 파지점 평가 기준(신뢰도, 안정성, 충돌 가능성 등)이 정의되어 있어야 한다.
- ROS2 제어 노드가 파지점 메시지를 수신할 준비가 되어 있어야 한다.

- 최적의 파지점(6D pose)이 선정되어 ROS2 제어 노드로 전달된다.

3. 가장 점수가 높은 후보를 최적 파지점으로 선택한다.
4. 선택된 grasp pose는 내부 저장 또는 `/vision/best_grasp_pose` 토픽으로 publish된다.
5. Command Executor Node는 이 토픽을 구독하거나 service 요청을 통해 값을 수신한다.

| Command Executor Node | Vision Node | ROS2 Service or Subscribe | 최적 파지점 수신 요청 또는 구독 |

# UC20 – 웹 UI를 통해 로봇 제어 명령 전송 (Send Robot Command via Web UI)

## 개요

|------|------|
| **유즈케이스 ID** | UC20 |

| **관련 기능 요구사항** | SR6. 웹 기반 제어 UI 제공 |
| **주 액터** | 운영자 (Web 브라우저 사용자) |
| **목적** | 웹 UI를 통해 로봇에게 Pick, Place, Door 제어, 이동 등의 명령을 전달한다. |

---

## 사전 조건

- 로봇 시스템과 Web UI 간 통신 연결이 정상 상태여야 한다.
- ROS2 노드 및 FastAPI 서버가 정상 구동되어 있어야 한다.

## 후 조건

- 명령 전송 성공 시 로봇이 지정된 동작을 수행한다.
- 명령 실행 결과(성공/실패)가 사용자에게 즉시 표시된다.

---

## 기본 흐름

1. 사용자가 Web UI에서 원하는 제어 명령 버튼을 클릭한다.
2. Web UI는 FastAPI 서버로 RestFul POST 요청을 전송한다.
3. FastAPI 서버는 해당 명령 요청을 ROS2 서비스 호출로 변환하여 Command Executor Node에 전달한다.
4. Command Executor Node는 명령을 해석하여 하드웨어로 실행 명령을 발행한다.
5. 실행 결과를 FastAPI에 회신한다.
6. FastAPI는 결과를 Web UI로 변환하여 사용자에게 표시한다.

---

## 예외 흐름

- **E1: API 통신 오류**  
  FastAPI 서버가 응답하지 않을 경우  
  → “명령 전송 실패” 팝업 또는 경고 표시

- **E2: ROS2 응답 지연/실패**  
  → 일정 시간 동안 결과가 수신되지 않으면 "명령 미응답" 상태 표시

---

## 통신 흐름

| 송신자 | 수신자 | 방식 | 메시지 |
|--------|--------|------|--------|

| FastAPI | Schedular Node | ROS2 Service Call | /Schedular_node/execute_command |
| Schedular Node | Command Executor Node | 내부 ROS2 통신 (Service/Request) | 명령 실행 요청 |
| Command Executor Node | H/W Node | 내부 ROS2 통신 (Service/Request) | 하드웨어 제어 명령 송신 |

---

## 비고

- 각 명령의 UI 컴포넌트는 명확한 피드백(로딩, 결과, 실패)을 제공해야 함
- 네트워크 지연에 대한 대처 메시지(로딩 표시, 재전송 버튼 등)도 포함 추천

# UC27 – 실시간 로봇 조인트 예측 요청 (ROS2 기반 통신 구조)

## 개요

| 항목 | 내용 |
|------|------|
| **유즈케이스 ID** | UC27 |
| **유즈케이스 명** | 실시간 로봇 조인트 예측 요청 |
| **관련 기능 요구사항** | F5-1. 로봇 행동 예측 기능 |
| **주 액터** | Vision_Node, Status_Node, AI_Node (AI PC), Status_Node or Command_Executor_Node |
| **목적** | 로봇의 실시간 이미지와 조인트 상태를 ROS2 네트워크를 통해 AI 노드로 전송하고, 다음 조인트 상태를 예측 받아 후속 처리에 활용한다. |

---

## 사전 조건

- `Vision_Node`는 ROS2를 통해 실시간 이미지(`/image_raw`)를 퍼블리시하고 있어야 한다.
- `Status_Node`는 `/joint_states` 토픽을 통해 로봇의 현재 조인트 상태를 퍼블리시 중이어야 한다.
- `AI_Node`는 ROS2 subscriber로 등록되어 있어야 하며, 추론 결과를 `/predicted_joint` 토픽에 퍼블리시할 수 있어야 한다.
- ROS2 통신 환경은 AI PC와 Backend PC 간에 QoS 및 네트워크가 안정적으로 구성되어야 한다.

---

## 후 조건

- AI PC에서 추론된 다음 조인트 값이 ROS2 토픽(`/predicted_joint`)으로 퍼블리시된다.
- 후속 노드(command_executor 등)가 해당 값을 구독하거나, FastAPI를 통해 UI로 전달된다.
- 추론 결과는 상태 확인 또는 실제 동작 실행 판단에 활용될 수 있다.

---

## 기본 흐름

1. `Vision_Node`가 실시간으로 카메라 이미지(`/image_raw`)를 퍼블리시한다.
2. `Status_Node`가 현재 로봇의 `/joint_states`를 퍼블리시한다.
3. `AI_Node`는 `/image_raw`와 `/joint_states`를 동시에 구독하여 입력값으로 사용한다.
4. `AI_Node`는 다음 시점의 예측된 조인트 값(예: [1.01, -0.53, 0.75, ...])을 `/predicted_joint` 토픽에 퍼블리시한다.
5. `Status_Node` 또는 `Command_Executor_Node`가 `/predicted_joint`를 구독하여 결과를 상태 처리 또는 실행 판단에 활용한다.
6. FastAPI는 필요 시 `/predicted_joint` 값을 WebSocket 등을 통해 Web_UI에 표시한다.

---

## 예외 흐름

- **E1: AI 노드가 연결되지 않음**  
  `/image_raw` 또는 `/joint_states` 구독 실패 → 로그 기록, fallback 모드 진입

- **E2: 추론 지연 또는 예측 실패**  
  AI 연산이 일정 시간 초과 또는 결과 미반환 → 이전 조인트값 유지 또는 skip

- **E3: 통신 지연**  
  ROS2 네트워크 QoS 설정 오류 또는 bandwidth 부족 → 이미지 프레임 누락, 예측 정확도 저하 가능

---

## 통신 흐름

| 구간 | 방식 | 내용 |
|------|------|------|
| Vision_Node → AI_Node | ROS2 Topic (`/image_raw`) | 실시간 이미지 프레임 (CompressedImage 또는 Image) |
| Status_Node → AI_Node | ROS2 Topic (`/joint_states`) | 현재 조인트 상태 벡터 |
| AI_Node → 전체 시스템 | ROS2 Topic (`/predicted_joint`) | 예측된 다음 조인트 상태 |
| FastAPI → Web_UI (옵션) | WebSocket | `/ws/predicted_joint` 등으로 UI 표시용 전달 |

## 비고

- ROS2 기반 구조는 이미지 + 조인트 벡터를 병렬로 처리하는 데 최적화되어 있음.
- 추론 주기 유지(30Hz)를 위해 AI_Node 내부에 buffer, queue, frame drop 제한 등 필요
- 추론 결과가 실제 로봇 제어에 반영될 경우, 별도의 안전 판단 로직 및 제한 조건 필수
